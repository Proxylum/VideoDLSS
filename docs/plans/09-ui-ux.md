# План этапа 9 — UI/UX: целевой поток, переиспользование и версии пассов

Дата: 2026-09-22. Ветки: `stage/09-ui-ux-<буква MR>` (этап слишком велик для одного MR — шесть MR в фиксированном порядке,
каждый со своими тестами и документацией). Основание: UX-аудит `dlssvid-gui` (рабочее пространство агента,
`Output/ux-audit/README.md`: 11 сценариев, 10 находок), макеты целевого потока (холст с Play-прототипом, исходники —
`Output/ux-mockups/`), принципы `docs/ux-guidelines.md`; решение пользователя 2026-09-22: переиспользование пассов по
отпечатку и версии пассов — принято, включить в план.

## Что не так сейчас (из аудита, по убыванию важности)

1. Таймлайн по номеру кадра, один индекс на источники с разной частотой (24 fps исходник, 48 fps результат): чёрные кадры без
   объяснения, сетка 2×2 не рисует существующие кадры (дефект `FrameStore`/`AppModel`).
2. Сравнение «до/после» — четыре шага через стек слоёв; новый слой по умолчанию `mv_raw` 50 %.
3. Параметры стадий — сырой JSON в ячейке, зависимости невидимы: NR без глубины/векторов считается молча.
4. Пустое состояние без подсказки, диалоги в папке `bin`, нет недавних и drag-and-drop.
5. Задачи без отмены, ETA, уведомления и перехода к результату.
6. Панели не восстанавливаются, раскладка не сохраняется, док проекта 115 px.
7. Статусы «частично: 240 из 479» у полных пассов; закрытие без вопроса о сохранении; внутренние имена пассов в UI.
8. Ядро: `ProcessRunner::PassComplete` переиспользует пасс по хэшу исходника и числу кадров — **параметры не сравниваются**:
   смена интенсивности NR не пересчитывает `color_nr`.

## Принятые решения

- **Отпечаток пасса** = sha256 от (хэш исходника, имя стадии, канонический JSON параметров, отпечатки входных пассов, версия
  инструмента: версия приложения, id модели/движка, sha256 DLL NVIDIA). Хранится в `manifest.json`. Пасс переиспользуется
  только при совпадении отпечатка; изменение параметра инвалидирует стадии ниже по цепочке автоматически.
- **Версии пассов: текущая на месте, предыдущие рядом.** `<passes>/<pass>/` остаётся текущей версией (никакой читатель не
  меняется), история — `<passes>/<pass>.v/<YYYYMMDD-HHMMSS_<fp8>>/`. При пересчёте с другим отпечатком текущая папка
  переносится в историю, новая пишется на место. Проект помнит отпечаток текущей версии каждой стадии; переключение версии —
  обмен папок. Хранятся две последние (настройка проекта `passVersionsKeep`), сборщик не удаляет версии, на которые
  ссылаются проект или входы других версий. Существующие папки без версий — это уже «текущая», миграции файлов нет.
- **Таймлайн по времени**: состояние вьюпорта хранит секунды; кадр каждого источника = round(t × fps источника);
  воспроизведение с максимальным fps среди слоёв; шаг кадра — по базовому слою.
- **Один главный путь**: Старт → Проект (карточки стадий с формами, одна кнопка «Обработать · N стадий») → Обработка →
  Результат «До | После». Инженерный режим (стек слоёв, сетка, пробник, JSON, лог, версии пассов) — переключатель, не
  отдельное окно.

## Что делаем (шесть MR по порядку)

### MR A — отпечатки, версии, план (`core/pipeline`, `core/passes`, `cli`)

1. `core/passes/Manifest`: поля `fingerprint`, `inputs` (пасс → отпечаток), `tool` (версия приложения, модель, движок,
   sha256 DLL), `paramsCanonical`; `core/pipeline/PassFingerprint.{h,cpp}`: канонизация JSON (сортировка ключей,
   нормализация чисел) и цепочка хэшей; `core/pipeline/PassVersions.{h,cpp}`: история `<pass>.v/`, `Retire(current)`,
   `Use(versionId)`, `List()`, `Gc(keep, referenced)`.
2. `ProcessRunner`: решение о переиспользовании по отпечатку; `Plan(options)` без запуска — по стадиям
   `{reuse | run, причина: params_changed (diff) | input_changed (stage) | missing | source_changed}`; `RunProcess`
   использует `Plan`, пишет отпечаток и версию в отчёт. `EncodePassToVideo` кодирует текущую версию.
3. CLI: `dlssvid process --plan [--json]`; `dlssvid passes list|use <pass> <version>|gc [--keep N]`.
4. Тесты: юнит — канонический JSON стабилен, отпечаток меняется от каждого компонента; интеграция — второй запуск
   `process` переиспользует всё; смена `nr.intensity` пересчитывает только nr → fg → encode, старый `color_nr` уходит в
   `.v/`, `gc --keep 2` оставляет две версии; `--plan` совпадает с фактическим прогоном; **регрессионный тест на пробел
   ядра** (смена параметра раньше переиспользовала пасс). Golden-тесты не меняются (тот же результат при тех же
   параметрах).
5. Документация: `docs/architecture.md` (раскладка версий, отпечаток), README (`--plan`, `passes`).

**Статус (2026-09-22): выполнено** — MR !19 (ветка `stage/09-ui-ux-a`): `PassFingerprint`, `PassVersions`, `PlanProcess` /
`DecideStage` в раннере, `process --plan` / `--keep-versions`, `passes list|use|gc`, `pass_versions_keep` в проекте;
15 новых тестов (юнит: канонический JSON, отпечаток, инструмент, версии, gc; интеграция: штампы, регрессия на пробел
ядра, восстановление из истории, усыновление, смена исходника, forced/incomplete/disabled, CLI). Отступления от
плана: `Retire(current)` → `RetirePassVersion`, `Use` → `UsePassVersion`; «проект помнит отпечаток текущей версии» не
понадобилось — источник правды манифест текущей папки, а совпадающая версия в истории восстанавливается сама
(`restore`); пассы без отпечатка усыновляются, а не пересчитываются.

### MR B — таймлайн по времени, сетка, состояния кадра (`core/viewport`, `app`)

1. `ViewportState`: `time` (с) вместо `frame`; `FrameStore`: fps и число кадров каждого источника, `FrameAt(source, t)`,
   статусы `Missing | Queued | Loading | Ready` на кадр; окно предзагрузки — по времени. Корень дефекта чёрных ячеек на
   кадре 239 найти и закрыть регрессионным тестом (источники 24 и 48 fps).
2. Рендерер: плашки «загрузка…» / «нет кадра» в ячейке вместо чёрного; заголовок ячейки — таймкод и кадр источника.
3. `TimelineWidget`: таймкод `00:04.98 / 00:10.00`, кадр базового слоя, переключатель fps (24/48) при разных частотах.
4. Статус пасса — относительно его собственного fps («готов, 240 кадров»).
5. Тесты: `AppModel` отображение времени в кадры для 24/48 fps, форматирование таймкода, `FrameStore` регрессия.

**Статус (2026-09-22): выполнено** — MR !NN (ветка `stage/09-ui-ux-b`): `ViewportState::time` (+ `legacyFrame`,
`FormatTimecode`), `FrameStore` с частотой на источник (`FrameAt`, `TexturesAt`, `Duration`, `ExpectedFrames`, окно
префетча в секундах, статус `Loading`), плашки `FrameStates` в рендерере и шейдере, `AppModel` (шаг по базовому слою,
частота таймлайна, воспроизведение с максимальной частотой), `TimelineWidget` с таймкодом и переключателем частоты,
подписи ячеек с кадром источника, таймкодом и состоянием, честный статус пассов в панели проекта, `render --time`.
Корень «чёрных ячеек»: скриншот аудита снят на индексе 246 результата (48 fps) — у 24-fps источников там нет кадра, а
плашки не было; рендер CLI на 239 показывал все ячейки. На временной оси кадр есть у каждого источника —
регрессионный тест 24/48 fps по всей шкале. +4 теста (198).

### MR C — сравнение одним действием (`app`, `core/viewport`)

1. Режимы «До | После» (шторка source↔result, позиция 50 %), «Только после», «Сетка 2×2»; хоткей W включает
   «До | После», если шторка не настроена.
2. Чипы слоёв с человеческими именами (Исходник, Глубина, Векторы, Апскейл, Улучшение, Генерация, Результат);
   технические имена — в подсказках; у чипа — список версий пасса (MR A) для сравнения версий шторкой.
3. Новый слой: 100 %, следующий неиспользованный источник; пресеты сравнений (SR↔NR, source↔depth).
4. Переключатель «Инженерный режим» показывает стек слоёв и секции инспектора; в обычном режиме они скрыты.
5. Тесты: app — переключение режимов, пресеты, состав чипов; `ViewportState` — сериализация новых полей.

### MR D — экран проекта: карточки стадий, зависимости, переиспользование (`app`, `core/stages`, `core/viewport/Project`)

1. Схема параметров стадии (`core/stages/<stage>/ParamSchema`: тип, диапазон, варианты, подпись, подсказка) — единый
   источник для валидации в `ProcessRunner`/CLI и форм в GUI (список бэкендов, переключатель масштаба, слайдер
   интенсивности); JSON-редактор остаётся в инженерном режиме.
2. Карточки стадий: состояние из `ProcessRunner::Plan` («переиспользуется · 0 мин», «пересчёт: интенсивность 1.0 → 1.4»,
   «пересчёт: изменился вход (из-за …)», «будет посчитано», «другой исходник»), принудительный пересчёт, предупреждение о
   зависимостях (NR/FG без глубины и векторов) до запуска.
3. Блок «Что получится»: разрешение, fps, звук; оценка времени по мс/кадр стадий (таблица `docs/benchmarks.md`,
   уточняется последними прогонами на этой машине), диск с учётом версий; кнопка «Обработать · N стадий».
4. Источник: хэш и его совпадение с пассами (кэш хэша по размеру и времени изменения файла).
5. Тесты: схема → валидация и форма, план → состояния карточек, арифметика оценок, кэш хэша.

### MR E — старт, раскладка, сохранность (`app`)

1. Стартовый экран: «Открыть видео…», «Открыть проект…», drag-and-drop, недавние (QSettings) с состоянием проекта, строка
   готовности GPU/драйвера/DLL.
2. QSettings: геометрия окна и доков, последние папки диалогов; меню «Вид» с пунктами панелей (`toggleViewAction`);
   стартовая ширина дока проекта по содержимому; окно на весь экран при первом запуске.
3. Несохранённые изменения: «*» в заголовке, вопрос при закрытии, автосохранение проекта рядом с видео.
4. Тесты: настройки туда-обратно, список недавних, логика вопроса при закрытии (на уровне модели).

### MR F — обработка: отмена, ETA, уведомление, переход к результату (`app/TaskQueue`, `core/pipeline`)

1. Отмена: завершение дочернего процесса, готовые пассы остаются; ETA по прошедшему времени и мс/кадр; общий прогресс по
   стадиям с переиспользованными, отмеченными сразу.
2. Фон: свёрнутое окно, системное уведомление (`QSystemTrayIcon`) по завершении; автоматический переход в «До | После».
3. Хвост лога на экране обработки, полный лог — в инженерном режиме.
4. Тесты: `TaskQueue` — отмена, расчёт ETA, порядок событий.

## Приёмка этапа

- Сценарий оператора «Открыть видео → Обработать → До | После → Сохранить» проходится без JSON и без стека слоёв.
- Смена интенсивности NR пересчитывает только NR, FG и кодирование; предыдущая версия NR доступна для сравнения шторкой;
  `gc` держит две версии.
- Таймлайн в секундах; при 24 и 48 fps кадры всех слоёв отображаются на всём диапазоне, состояния «загрузка» и «нет кадра»
  подписаны; сетка 2×2 на кадре 239 рисует все ячейки.
- Все находки аудита 1–8 закрыты; 179+ тестов зелёные, CI зелёный; golden без изменений.

## Риски и как их снимаем

- Версии удваивают место на диске — лимит «две последние» и `gc` входят в MR A, а не позже; размер версий виден в UI.
- Переход `frame → time` задевает тесты этапа 4 (`AppModel`, `TimelineWidget`) — правятся вместе с кодом, старое поле
  читается из проектов как `time = frame / fps` (обратная совместимость файла проекта).
- Схема параметров дублирует опции CLI — CLI сохраняет свои флаги, но валидирует значения той же схемой (один тест на
  расхождение).
- Пробел ядра (параметры не сравниваются) закрывается первым (MR A), чтобы остальные MR опирались на честное
  переиспользование.
