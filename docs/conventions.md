# Конвенции пассов (raw ↔ DLSS)

Формулы, единицы и знаки зафиксированы здесь один раз и реализованы в `core/convert/`
(`DepthConvert`, `MvConvert`, `ColorConvert`). Юнит-тесты: `tests/unit/test_depth_convert.cpp`,
`test_mv_convert.cpp`, `test_color_convert.cpp`. Форматы файлов и манифест — `core/passes/`.

## 1. Общие соглашения

- Кадры нумеруются с 0 в порядке декодирования; пасс хранит по одному файлу на кадр.
- Координаты изображения: `x` вправо, `y` вниз, начало в левом верхнем углу; центр пикселя
  `(x + 0.5, y + 0.5)`. Все векторы в пикселях того разрешения, в котором записан пасс
  (`mv.ref_width/ref_height` в манифесте, 0 = разрешение файла).
- Типы сэмплов: `u8`, `u16`, `f16` (IEEE binary16), `f32`.
  - **Цвет и маски** означают [0,1]. В целых типах это полный диапазон: u16 = round(v·65535), u8 = round(v·255).
    `PassWriter` такого пасса нормирует сам, в обе стороны (`PassImage::ConvertNormalizedTo`). Так же их читают
    `ToRgba16f`, `RgbToYuv` и загрузчики масок.
  - **Глубина и векторы** хранят значения как есть (`PassImage::ConvertTo`).
  - До TASK-0042 цветной пасс в PNG16 из стадий писался без масштаба, то есть почти чёрным.
- Внутреннее представление одного кадра пасса — `PassImage`: interleaved-каналы, построчно,
  без выравнивания.

## 2. Глубина

| Пасс | Значение | Единицы | Больше = |
|---|---|---|---|
| `depth_raw` | линейная глубина вдоль оси камеры | метры (`depth.units = meters`) или относительные (`relative = true`) | дальше |
| `depth_dlss` | reverse-Z, вход DLSS | [0, 1] | **ближе** (1 = near plane, 0 = far plane) |

Reverse-Z с конечной far-плоскостью (`near`, `far` — метры, `0 < near < far`, из манифеста):

```
d = near · (far − z) / (z · (far − near))            z ∈ [near, far] → d ∈ [1, 0]
z = near · far / (d · (far − near) + near)            обратное преобразование
```

Проверки: `z = near → d = 1`, `z = far → d = 0`, `z = 2·near·far/(near+far) → d = 0.5`;
округление float32 даёт относительную ошибку round-trip < 2·10⁻⁵ (тест).

Правила:
- `z` вне `[near, far]` клампится; `z ≤ 0`, NaN, ±inf → `d = 0` (far).
- Относительная глубина: `z_m = near + (v − min) / (max − min) · (far − near)`; `min`/`max`
  берутся из манифеста (`depth.min/max`), при нулях вычисляются по первому кадру и записываются
  в манифест, чтобы обратное преобразование было точным. `max == min` → всё на near.
- Обратное преобразование `depth_dlss → depth_raw` при `relative = true` возвращает исходные
  относительные единицы.
- `depth_raw` пишется после временного выравнивания (TASK-0038): `stage_params.stabilize` — что применено
  (`none` | `scale` | `scale_shift`), `stabilize_requested` — что запрошено (`auto` …), `stabilize_window` — радиус N
  (кадр выровнен по t−N…t+N), `stabilize_scale` / `stabilize_shift` — диапазон применённого преобразования. Сырой выход
  модели — `--stabilize none`.

## 3. Motion vectors

| Пасс | Что хранит в кадре `t` | Направление | Единицы |
|---|---|---|---|
| `mv_raw` | forward optical flow `F_t` | `p(t+1) = p(t) + F_t(p(t))` (t → t+1) | пиксели исходного разрешения |
| `mv_dlss` | backward-векторы `B_t` | `p(t−1) = p(t) + B_t(p(t))` (t → t−1) | пиксели целевого (render) разрешения |

Оба — 2 канала `u` (x) и `v` (y), `y` вниз (`mv.y_up = false`). Внешний пасс с `y` вверх помечается
`mv.y_up = true` (папке без манифеста флаг задаёт `import` / `convert` / `export --from-dir` с `--y-up`); флаг
описывает только знак `v`, строки изображения по-прежнему идут сверху вниз. Любое чтение кадра такого пасса
(`PassReader::ReadFrame`: слоты upscale / nr / fg, `depth --mv-dir`, `convert`, `import --to-dlss`,
`export --from-dir`, вьюпорт и его пробник, `render`) меняет знак `v` (`FlipMvY`), дальше данные уже в конвенции
DLSS; манифест папки при этом не переписывается. Пассы, которые пишет dlssvid (flow, convert, export), всегда
несут `y_up = false`. Флаг требует сэмплов f16 / f32 — с u8 / u16 пасс отклоняется. Флаг задаётся при импорте, а не
правкой манифеста пасса с отпечатком: смена флага у внешнего пасса без отпечатка пересчитывает стадии ниже
(псевдо-отпечаток `legacy:<hash>:<frames>:y_up`).

Конвертация `mv_raw` → `mv_dlss` (кадр `t+1` получается из flow кадра `t`):

1. **Инверсия (splat вперёд).** Для каждого пикселя `q` кадра `t`: `p = round(q + F_t(q))`;
   если `p` внутри кадра, `B_{t+1}(p) = −F_t(q)`. Коллизии (несколько `q` попали в один `p`)
   разрешаются по глубине кадра `t` — **ближайшая** поверхность (меньшее `depth_raw`) побеждает;
   без глубины побеждает последний записанный.
2. **Заполнение дыр.** Пиксели, в которые никто не попал (открывшиеся области), получают вектор
   ближайшего заполненного пикселя (BFS от заполненных).
3. **Дилатация по границам глубины** (радиус 1–2 px, `--dilate`): пиксель берёт вектор
   ближайшего по глубине соседа в окне, если тот ближе более чем на `depthEdgeThreshold`
   (2 % относительной глубины). Так DLSS получает «толстые» векторы у краёв объектов.
4. **Масштаб** под целевое разрешение `(W', H')`: nearest-ресемпл и умножение `u·W'/W`, `v·H'/H`.

Первый кадр последовательности не имеет предыдущего — его `mv_dlss` нулевой; последний кадр не имеет следующего — его `mv_raw` нулевой (стадия flow, этап 3). Обратная
конвертация `mv_dlss → mv_raw` — та же инверсия (кадр `t−1` из `B_t`), последний кадр нулевой.
Для чистого сдвига обе конвертации точны и взаимно обратны (тест).

### 3.1. Источники flow (этап 3)

| Бэкенд | Что | Единицы на выходе |
|---|---|---|
| `ofa` | NVIDIA Optical Flow Accelerator (`nvofapi64.dll`, CUDA), вход NV12 прямо из NVDEC или ABGR8 из CPU; выход `NV_OF_FLOW_VECTOR` S10.5 на сетке grid×grid (запрашивается 1) | `flow / 32` → пиксели полного разрешения; сетка > 1 апсемплируется билинейно; cost-буфер → confidence = 1 − cost/255 |
| `searaft` | SEA-RAFT (Spring-M, 4 итерации) через TensorRT из ONNX `(image1, image2: 1×3×H×W RGB 0..255) → flow 1×2×H×W`; геометрия — исходное разрешение, ограниченное `--max-res` по короткой стороне и кратное 8 | пиксели геометрии модели, масштабируются под источник (`ScaleMv`) |

Warp-тест (ТЗ §8): `WarpBackward(prev, mv_dlss_t)(p) = prev(p + mv_dlss_t(p))` должен совпадать с `cur`;
PSNR считается по валидным сэмплам (внутри кадра). TAE с компенсацией движения:
`mean |d_t(p) − d_{t−1}(p + mv_dlss_t(p))| / mean d_{t−1}`.

## 4. Цвет

`color_source` из декодированного планарного YUV в раскладке источника (8, 10, 12 или 16 бит; 4:2:0,
4:2:2 или 4:4:4): display-referred RGB (sRGB/BT.709 передаточная функция, без линеаризации), диапазон
[0, 1]. Матрица и диапазон — из метаданных потока, иначе BT.709 для ≥ 720 строк и BT.601 ниже;
ограниченный диапазон при N битах (8 бит: 16 / 219 / 128 / 224; 10 бит: 64 / 876 / 512 / 896):

```
Y' = (Y − 16·2^(N−8)) / (219·2^(N−8)),  Cb = (U − 128·2^(N−8)) / (224·2^(N−8)),  Cr = …      (full range: /(2^N − 1))
R' = Y' + 2(1−Kr)·Cr
G' = Y' − 2Kb(1−Kb)/Kg·Cb − 2Kr(1−Kr)/Kg·Cr
B' = Y' + 2(1−Kb)·Cb
BT.709: Kr = 0.2126, Kb = 0.0722;  BT.601: Kr = 0.299, Kb = 0.114;  Kg = 1 − Kr − Kb
```

Хрома реплицируется на блок (2×2 при 4:2:0, 2×1 при 4:2:2, без интерполяции) — результат детерминирован
и обратим поблочно; обратная конверсия усредняет блок и округляет к ближайшему коду целевой разрядности.
Значения клампятся в [0, 1]. Использованные матрица и диапазон записываются в
`stage_params.matrix` / `stage_params.range` манифеста. Линейный (scene-referred) цвет и тонмаппинг —
стадии 5–6; ключ `colorspace` в манифесте тогда будет `linear`.

## 5. Форматы файлов

| Формат | Расширение | Типы | Каналы | Примечания |
|---|---|---|---|---|
| OpenEXR | `.exr` | f16, f32 (u8→f16, u16→f32 при записи, восстанавливаются по манифесту) | по именам: `R,G,B`, `Z`, `u,v`, `A` | ZIP-сжатие, без потерь. Multi-layer: `depth.Z`, `mv.u`, `mv.v` |
| PNG | `.png` | u8, u16 | 1–4 (gray, gray+alpha, RGB, RGBA) | big-endian на диске; float не пишется: `PassWriter` цвета и масок переводит [0,1] в полный диапазон, остальное — конвертировать явно |
| TIFF | `.tif` | u8, u16, f16, f32 | 1–4, contiguous | Deflate, без потерь |
| NumPy | `.npz` / `.npy` | u8, u16, f16, f32 | массив `(H, W)` или `(H, W, C)`, C-order, little-endian | ключ = имя пасса; запись stored, чтение stored + deflate (`savez_compressed`) |
| Бинарь | `.r32`, `.rg16f`, `.r16f`, `.rg32f`, `.r8` … | по расширению | по расширению | без заголовка, размер из манифеста |

## 6. Манифест (`manifest.json`, schema_version 1)

```json
{
  "schema_version": 1,
  "pass": "depth_raw",
  "width": 1920, "height": 1080,
  "fps": {"num": 24000, "den": 1001},
  "frame_count": 240, "frame_range": {"first": 0, "last": 239},
  "format": "exr", "file_pattern": "depth_raw_%06d.exr",
  "pixel_type": "f32", "channels": ["Z"],
  "colorspace": "",
  "convention": "raw",
  "model": {"name": "depth-anything-3", "version": "1.0"},
  "source": {"file": "clip.mp4", "hash": "sha256:…"},
  "stage_params": {},
  "depth": {"units": "meters", "relative": false, "near": 0.1, "far": 1000.0, "min": 0, "max": 0},
  "mv": {"direction": "forward", "y_up": false, "ref_width": 0, "ref_height": 0},
  "fingerprint": "sha256:…",
  "inputs": {"color_sr": "sha256:…", "depth_dlss": "sha256:…", "mv_dlss": "sha256:…"},
  "tool": {"app": "0.1.0+nr.gain", "backend": "ngx", "model": "", "model_hash": "", "dll_file": "nvngx_dlssnr.dll", "dll": "sha256:…"},
  "params_canonical": {"backend": "ngx", "intensity": 1.4},
  "created": "2026-09-22T14:09:31Z"
}
```

Последние пять полей (этап 9) пишет `dlssvid process` (`fingerprint` — ещё и `import --stamp`, см. ниже): `fingerprint` — отпечаток прогона, по которому пасс
переиспользуется (`docs/architecture.md`, «Отпечатки и версии пассов»), `inputs` — отпечатки прочитанных пассов,
`tool` — версия приложения, бэкенд, модель и sha256 NVIDIA DLL, `params_canonical` — параметры стадии в
канонической записи, `created` — время завершения (UTC). У пассов, записанных `dlssvid <stage>` вручную или до
этапа 9, полей нет — такой пасс «текущий» и усыновляется первым `process` (кроме пасса NR с `stage_params.ab` —
переключатели A/B отдельного `dlssvid nr`: он не усыновляется, не переиспользуется, не восстанавливается, не берётся
входом стадий или результатом и при пересчёте уходит в историю версий). Предыдущие версии пасса лежат рядом:
`<pass>.v/<YYYYMMDD-HHMMSS_<fp8>>/` (тот же формат папки).

`stage_params.ms_per_frame` — wall-время мс/кадр прогона `process` на этой машине (его пишет раннер), по нему считаются
оценки. У `color_nr` стадия его не пишет: её GPU-время — `stage_params.ms_per_frame_gpu` (отправка и ожидание command list на
кадр, кадры прогрева включены); его пишет и отдельный `dlssvid nr` (TASK-0049). Так же апскейл пишет `ms_per_frame_gpu`, а FG —
`ms_per_frame_backend` (время бэкенда на реальный кадр); `ms_per_frame` эти стадии не пишут (TASK-0051). Оценки берут запись
NR, апскейла и FG только рядом с таймером стадии. Запись без него сделана раньше: это мог быть и таймер стадии отдельного или
усыновлённого пасса, и wall-время `process` поверх него — различить их нельзя, поэтому до пересчёта стадии берётся базовое
время.

`color_nr` пишет силу правки: `stage_params.intensity` — наша сила после модели, `model_intensity` — что получила модель
(всегда 1; поле — признак пасса PR-7: пасс NR без него с `intensity ≠ 1` снят до PR-7 и отбрасывается). При `intensity 0`
модель не вызывается: `bypass: true`, `passes: 0`, `model_intensity` нет. `stage_params.vram_mib_per_pass` — видеопамять фичи
каждого прохода (рост `CurrentUsage` процесса по DXGI на её `CreateFeature`, МиБ; PR-5; у stub — 0, фичи у него нет); без
замера (DXGI не отдал память) поля нет.

**Склейки (PR-13).** Пасс `scenes` — пасс данных: `channels: []`, кадров нет, `frame_range` — проанализированные кадры
исходника, размер и fps — исходника. `stage_params`: `threshold`, `off` (порог 0), `scene_cuts` (кадры, каждый начинает
план; отсортированы, без 0), `scene_cut_count`, `cuts_id` (`cuts:` + sha256 JSON списка; пустой список — `""`), `near`
(до 5 пар `[кадр, оценка]` чуть ниже порога), `analysis` (`algorithm` `luma-mad.640`, `max_width`, `ms_per_frame`,
`source_format`, `reached_end`, `frames`, `scores_file` `scores.npy`, `scores_count`, `scores_sha256`), у пересчёта по
оценкам — `rederived: true`. `scores.npy` — оценка каждого кадра к предыдущему (N×1 F32, канал `score`, кадр 0 — 0). Стадия,
прочитавшая список, пишет метку: `scene_cuts_id` (id списка), `scene_cut_threshold`, `scene_cut_count` и `scene_cuts` —
склейки, применённые в её кадрах (не больше 1000); FG ещё `duplicated` — кадры, повторённые вместо интерполяции; оконный
апскейл — `window_breaks`. Без списка этих ключей нет. Во `inputs` такой стадии — `"scenes": "<cuts_id>"`.

У импортированного пасса (маски `mask_*`, внешняя глубина) отпечатка нет. Для стадий, которые его читают, он
означает только «источник и число кадров», поэтому замена содержимого с тем же числом кадров не пересчитывает их.
`dlssvid import -i <папка> --stamp` записывает в манифест отпечаток содержимого (TASK-0045). Это sha256 канонической
записи: имя пасса, то, как читаются файлы (манифест без полей происхождения: размер, формат, каналы, `mv.y_up`,
диапазон глубины), и sha256 каждого кадра. Импорт с новым содержимым и `--stamp` пересчитывает NR. Из флагов прогона
(`--y-up`, `--near`, `--far`, `--relative`) в манифест папки с манифестом ничего не попадает, меняется только
`fingerprint`. С `--to-dlss` / `--to-raw` штампуется сконвертированный пасс, а не исходный. Если файлы подменить без
повторного `--stamp`, это не отслеживается. То же с правкой манифеста, например `mv.y_up`: после неё повторите
`--stamp`.

Так `import --stamp` становится вторым, после `dlssvid process`, писателем поля `fingerprint`. Остальные поля версии
(`inputs`, `tool`, `params_canonical`, `created`) у такого пасса пустые.

NR с `guides: false` не читает `depth_dlss` и `mv_dlss`: это не входы его отпечатка, и новая глубина сама по
себе его не пересчитывает (через новый `color_sr` — пересчитает, если апскейл на ней).

Числа в отпечатке канонизируются до 9 значащих цифр. 0.30000000000000004 с ползунка и 0.3 из JSON — один прогон.

Пасс клипа начинается с кадра 0; номера кадров в именах файлов абсолютные. Отрезок (`dlssvid nr --start F`) пишет кадры
F…L: их называет `frame_range`, а `stage_params.range = {first, last, warmup}`. `process` считает такой пасс неполным и
пересчитывает (TASK-0047), а входом других стадий и результатом его не берёт. `compare --start` считает кадры от первого
кадра каждой папки.

Импорт без манифеста: папка сканируется по нумерованным файлам одного формата, пользователь
указывает `--pass` (и `--convention`, `--size WxH` для бинарных дампов, `--y-up` для векторов с осью `y` вверх);
`--write-manifest` сохраняет восстановленный манифест. `--y-up` у папки, в манифесте которой `y_up = false`,
действует только на этот прогон: манифест не меняется, CLI предупреждает. При импорте проверяются разрешение, число кадров и
непрерывность нумерации — несовпадение перечисляется в ошибке.

### 6.1. Заметка о настройках в результате (PR-11)

Результат `dlssvid process` несёт в метаданных контейнера, что его сделало:
- `comment` (все контейнеры; mkv, mp4, mov): `VideoDLSS <версия> | scenes: luma threshold=0.24 cuts=3 | upscale: dlss x2
  quality=… | nr: ngx style=natural intensity=1.2 passes=1 … | fg: dlssg x2` — одна ASCII-строка до 1 КБ, только стадии цепочки
  (сегмент `scenes` — по первой метке списка, встреченной от кодируемого пасса назад; без неё сегмента нет)
  кодируемого пасса, значения из их `stage_params`; усыновлённый пасс — `(adopted)`, обход модели NR — `(no model)`;
- `DLSSVID_SETTINGS` (только Matroska): `{"app": "VideoDLSS <версия>", "stages": {"upscale": {…}, "nr": {…}, "fg": {…}}}`.

`ReadContainerTags` (и `dlssvid info`) отдаёт ключи в нижнем регистре: Matroska хранит `COMMENT`. Цепочку стадий заметка
берёт из `stage_params.color_source`: у FG — `pass:<папка>`, `slot:color_nr`, `slot:color_sr` или `video`.

Путей машины в заметке нет. Ключ проекта `encode.settings_note` (по умолчанию `true`), в CLI — `process --no-settings-note`.

```
dlssvid import  -i out/depth_raw [--expect-size 1920x1080 --expect-frames 300] [--to-dlss out/depth_dlss --near 0.1 --far 1000]
dlssvid convert -i out/mv_raw -o out/mv_dlss --to mv_dlss --target 3840x2160 --depth-dir out/depth_raw --dilate 1
dlssvid import  -i ext/mv --pass mv_raw --y-up --write-manifest           (векторы другого инструмента с осью y вверх)
dlssvid import  -i out/mask_skin --stamp                                  (отпечаток содержимого: новая маска пересчитывает NR)
dlssvid passes  list|use <pass|stage> <version>|gc [--keep N] [--dry-run]  --passes out | --project clip.dlssvid.json   (этап 9: версии пассов)
dlssvid process -i clip.mp4 --param-file anime.json [--param-file nr=soft.json] [--param nr.intensity=0.9]   (PR-9: пресеты, §8)
dlssvid nr      -i clip.mp4 -o out --params-file soft.json                  (объект ключей nr или dlssvid-preset)
```

## 8. Пресеты `dlssvid-preset` (PR-9)

Пресет — именованный файл настроек, который GUI сохраняет и применяет, а CLI читает. Код — `core/stages/StagePreset`
(формат, проверка, применение), `core/stages/PresetLibrary` (папка, имена файлов, слоты), `core/viewport/PipelinePreset`
(пресет обработки над проектом); в GUI — `app/PresetStore`, `app/PresetMenu`.

```json
{
  "format": "dlssvid-preset", "schema": 1, "scope": "pipeline", "name": "Аниме 4K",
  "created": "2026-10-26T15:10:00Z", "app": "0.5.0",
  "stages": {
    "scenes":  {"enabled": true,  "params": {"threshold": 0.3}},
    "upscale": {"enabled": true,  "params": {"scale": 2, "backend": "dlss", "sharpness": 0.5, "preset": "default", "...": "..."}},
    "nr":      {"enabled": true,  "params": {"style": "natural", "intensity": 0.8, "...": "...", "backend": "ngx", "format": "exr"}},
    "fg":      {"enabled": false, "params": {"multiplier": 2, "backend": "dlssg", "model": "rife49", "...": "..."}}
  },
  "encode": {"codec": "hevc_nvenc", "bit_depth": "10", "chroma": "auto", "options": {"b": "50M"}}
}
```

Строки `"...": "..."` — сокращение примера: в файле их нет, у пресета из GUI все шесть стадий и все ключи их класса.

- **Вид** — обязательное поле `scope`. `"stage"` — пресет карточки (меню «Пресет ▾» карточки «Улучшение»): ровно одна стадия
  `{params}`, ключи формы (уровни Basic и More схемы). `"pipeline"` — пресет обработки («Пресет обработки ▾» в шапке
  «Стадии»): стадии `{enabled, params}` и секция `encode`. Пресет узнаётся по **значению** `format` (у стадий есть свой ключ
  `format`).
- **Какие ключи.** Пресет карточки — ключи формы своего бэкенда (`IsPresetKey`): без инженерных ключей, поэтому применение
  пресета NR не меняет ни `backend`, ни формат пасса. Пресет обработки — ключи формы и **тонкие настройки алгоритма**
  (`ParamSpec::tuning`: резкость NIS, пресет DLSS, `jitter`, модель RIFE, `z_near`/`z_far`, формат пасса, метод NR …).
  **Ключи машины** не входят ни в какой пресет: пути (`models_dir`, `python`) и размеры под видеопамять (`max_res`,
  `depth.input_size`, `upscale.tile`, `fp32`). Новый инженерный ключ схемы по умолчанию не `tuning`; тест требует решить, к
  какой группе он относится. Ключ формы со списком без списка у бэкенда (`depth.model` под DA3 из JSON) не ключ пресета.
  Маски — пассы, а не ключи, и в пресет не входят.
- **`encode`** — поля карточки «Кодирование»: `codec` из `KnownCodecs()`, `bit_depth` (`auto`, 8, 10, 12 — строкой или
  целым) и `chroma` (`auto`, 420, 422, 444), которые кодек кодирует, `options.b` — целые 1–400 Мбит/с у кодеков с битрейтом
  (`"50000k"` записывается как `"50M"`). Невозможная пара (H.264 + 10 бит) — отказ при чтении. `settings_note` и остальные
  опции кодера в пресет не входят: их переносит только файл проекта.
- **Полнота.** Пресет из GUI полный: у стадии записаны все ключи её класса, умолчания тоже; у пресета обработки — все шесть
  стадий и `encode`. Внутри стадии отсутствующий ключ значит умолчание (пресет описывает карточку целиком); отсутствующая
  стадия или `encode` значит «не трогать» (заметка `MissingStage` / `NoEncode`).
- **Чтение** (`ValidatePreset`, все проблемы за один проход). Отказ целиком: файл > 1 МиБ, не JSON, не пресет, `schema` не
  целое ≥ 1 или новее этой сборки, неизвестный `scope`, у пресета карточки не одна стадия, имя не 1–120 кодовых точек или с
  управляющими символами, значение вне диапазона, не того типа или не из списка, невозможное кодирование. С заметкой
  отбрасываются: незнакомый ключ, ключ не своего класса (`EngineerKey`), переехавший ключ (`nr.scene_cut` → `scenes.threshold`),
  незнакомая стадия, незнакомое поле, поле `encode` без строки в карточке, битрейт кодека без битрейта. Голый объект ключей
  стадии (`--params-file`, `--param-file stage=`) читается как раньше: незнакомый ключ — отказ (TASK-0047).
- **Применение** (`ApplyPreset`): бэкенд, который пресет называет (ключ его класса), переключается первым
  (`ParamsForBackendChange`); затем ключи класса заменяются — ключ, которого нет в пресете, возвращается к умолчанию, — а
  остальное остаётся: ключи вне класса, незнакомые ключи, ключ списка без списка. Ключи, равные умолчанию, в проект не пишутся
  (кроме `backend`). Пресет обработки так применяет каждую названную стадию, заменяет её `enabled` и поля «Кодирования»;
  результат получает контейнер кодека (`ResultPathFor`).
- **Миграции.** `schema` поднимается, когда меняется смысл или единицы ключа (старое значение выполнилось бы иначе); вместе с
  ним поднимается `schema_version` проекта. Удалённый ключ отбрасывается с заметкой, новый берёт умолчание, переехавший —
  запись в `MovedParam`. Новое значение `scope` — не повод поднимать `schema`: старая сборка отвергнет его как неизвестный вид.
- **Папка** — `QStandardPaths::AppDataLocation/presets`, на Windows `%APPDATA%\dlssvid\dlssvid\presets` (документы
  пользователя, роумятся с профилем). Оба вида лежат вместе, вид читается из файла. Имя файла — `PresetFileStem(name)`:
  `<>:"/\|?*` и управляющие символы → `_`, имена устройств Windows с префиксом `_`, не больше 80 байт; занятая основа —
  ` (2)`, ` (3)` (поверх существующего файла новый пресет не пишется никогда). Источник правды — поле `name`. Меню разбирает
  первые 500 файлов, остальные считает.
- **Слоты** `auto/before-apply-<цель>.json`, `auto/before-reset-nr.json` (цель — стадия или `pipeline`): состояние перед
  применением и сбросом, один шаг назад этой машины, всегда перезаписывается. Слот — снимок: его значения не проверяются
  (`PresetRead::Slot`), поэтому ошибка, которую проект хранит (`libx264`, H.264 + 10 бит), запись не срывает; применение
  слота возвращает её с заметкой. Экспорт слота строгий.
- **«Для новых проектов»** — одна метка, QSettings `presets/newProject` (имя файла в папке): пресет обработки сеет все стадии,
  включение и кодирование, пресет NR — только NR. Посев — в `AppModel::openVideo` для видео без файла проекта рядом. CLI метку
  не видит: его эквивалент — `--param-file`.
- **CLI.** `dlssvid nr --params-file` берёт пресет карточки nr или запись nr пресета обработки. `process` и `bench`:
  `--param-file <stage>=<file>` (голый объект — слияние поверх, пресет — его ключи стадии) и `--param-file <preset>` без
  `stage=` (пресет обработки — стадии и кодирование, пресет карточки — в свою стадию). Порядок слоёв: проект < пресет
  обработки < `--stages` < файлы стадий (по порядку строки) < `--*-backend`/`--scale`/`--multiplier` < `--param`; кодирование:
  проект < пресет < `--codec`/`--bit-depth`/`--chroma`/`--codec-opt`. Файл стадии её включает, как `--param`. `--plan`
  печатает строку `encode:` и пишет `encode` в `--json`.
