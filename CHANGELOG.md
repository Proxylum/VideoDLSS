# Изменения

Формат версий — semver; версия задаётся в `CMakeLists.txt` (`project(dlss-video VERSION …)`), пакет —
`dlss-video-<версия>-win64.zip` (`docs/release.md`). Версия релиза **не** входит в отпечатки пассов: за них отвечает версия
алгоритма пассов (`kPassToolVersion`, `core/pipeline/PassFingerprint.h`), которую поднимают только когда результат стадии
меняется при тех же параметрах.

## Не выпущено

- Детальные настройки DLSS 5, шаг 1 (TASK-0043, по разбору Visual Enhancer). **Ломающие изменения:**
  - **Экспозиция NR в ступенях EV.** `nr.exposure` и `dlssvid nr --exposure`: свет × 2^EV, 0 — без изменений,
    диапазон −8…8. Раньше это был линейный множитель с умолчанием 1, а схема и форма показывали умолчание 0, так что
    явное `"exposure": 0` давало чёрные кадры.
  - **Формат проекта `schema_version 2`.** Проекты версии 1 переводятся при открытии: множитель x становится log2(x)
    ступеней, x ≤ 0 удаляется, `skin_structure` между −1 и 0 становится −1. Старые сборки проекты версии 2 не откроют.
  - **Пассы NR, снятые со старой экспозицией, отличной от 1, пересчитываются.** Это касается и явного 0, который давал
    чёрные кадры; такие пассы не восстанавливаются из истории. Пассы со старым умолчанием переиспользуются. Новые
    значения `exposure ≠ 0` получили ревизию `+nr.ev`.
  - **`process --project P -i other.mp4`.** Другое видео получало хэш источника P: переиспользовало его пассы и писало
    результат поверх результата P. Теперь у него свой хэш, а пассы и результат по умолчанию — рядом с ним. То же видео,
    перенесённое в другое место (то же содержимое), остаётся видео проекта.
  - **Стадия в `process` запускается ровно с теми параметрами, что идут в отпечаток.** Раньше стадия получала сырые
    параметры проекта, а в хэш шли параметры схемы. Теперь умолчания схемы подставляются. Kebab-псевдонимы
    (`model-scale` и другие, `fg.backbuffer-format`) и `no_guides` приводятся к ключам схемы и проверяются по ним: раньше
    `{"model-scale": 0.5}` шло в прогон как 0.5 при отпечатке 1.0, а `{"local-tone": 5}` не проверялось.
  - **`flow.hwaccel` теперь только у бэкенда OFA.** searaft и stub всегда декодировали на CPU, но в отпечаток попадало
    `"cuda"`. Их пассы flow пересчитаются один раз, а вместе с ними и всё, что после flow.
  - **Разовые пересчёты.** NR и FG пересчитываются один раз у проектов, где была задана явная старая экспозиция, даже
    1: её ключ мигрирует, и отпечаток меняется.
  - **Устаревший пасс отбрасывается, а не уходит в историю.** Это PNG16 до TASK-0042 и NR со старой экспозицией. Его
    отпечаток при пересчёте не меняется, поэтому стадии, построенные на нём (FG после чёрного NR), тоже пересчитываются.
  - `depth.python: ""` (пустое поле) больше не ломает запуск воркера глубины.
- Исправлено (TASK-0042): цветной пасс в PNG16 (`upscale`, `nr` или `fg --format png16`, `format: png` в проекте)
  писался без масштаба — 0.5 становилось 1 из 65535, и кадры с результатом выходили чёрными.
  - Теперь `PassWriter` цветного пасса или маски сам переводит [0,1] в полный целый диапазон и обратно.
  - Заодно исправлено: `export` PNG16 → EXR больше не пишет 0…65535 в half-файл; пресет `nuke` из пасса PNG16 и FG
    с цветным пассом PNG16 на входе переводят цвет в [0,1].
  - Цветные пассы PNG16 upscale / nr / fg, записанные до исправления, испорчены. План узнаёт их по файлу: пасс в PNG,
    у инструмента которого нет ревизии `+png.2`. Такие пассы, в том числе без отпечатка (от отдельного `dlssvid nr
    --format png16`), не переиспользуются, не восстанавливаются из истории и не усыновляются, а пересчитываются.
  - Не узнаются автоматически: EXR из `export` пасса PNG16 и пресета `nuke` (там лежали значения 0…65535) и `color_fg`,
    сделанный из внешнего цветного пасса PNG16 (реальные кадры без масштаба). Их нужно пересчитать вручную.
  - Плавающие EXR-маски, импортированные без манифеста, теперь сохраняют значения [0,1]. Раньше манифест получал u8,
    и 0.5 округлялось до 0 или 1.
- Перемотка случайными прыжками ≥ 30 fps на 1080p (TASK-0040, аудит scrub-30fps, ТЗ §9(6)). Для видео с длинным GOP
  строится прокси для перемотки — lossless-копия кадров бит-в-бит (MagicYUV для 8 бит, FFVHuff для 10–16 бит) в
  `<пассы>/.proxy`: GUI строит её в фоне после открытия проекта (не больше 8 ГБ и четверти свободного места; «Вид» →
  прокси автоматически / построить / удалить), CLI — `dlssvid proxy`. Прыжок по 1080p — p90 15 мс (было 199–348 мс),
  сетка 2×2 — 21 мс, 10 бит — 25 мс. Загрузчики кадров: прыжок не ждёт префетч соседей, ненужные загрузки снимаются
  без потери кадра при возврате, конверсия YUV → RGBA16F на нескольких потоках, пассы EXR читаются параллельно,
  текстуры готовятся вне потока рендера. `render --bench` меряет только промахи (p50 / p90, `--bench-json`,
  `--bench-mode`, `--proxy auto|off|build`); в логе GUI — задержка прыжков («viewport scrub»).
- Выбор модели VDA: Small / Base / Large (TASK-0039). В карточке «Глубина» для VDA (TensorRT) и нового бэкенда «VDA
  через PyTorch» (`worker:vda`) — список моделей с лицензией: Small (Apache-2.0, по умолчанию), Base и Large
  (CC-BY-NC-4.0, только некоммерческое использование — предупреждение в плане и на карточке, ONNX не входит в полный
  пакет); окно кадров VDA (`depth.window`, кратно 4, 0 = из реестра). CLI: `dlssvid depth --model … --window N`,
  `process --param depth.model=…`. Модель проверяется по реестру до декодирования и экспорта: чужая или неизвестная —
  ошибка со списком моделей семейства. План оценивает видеопамять по замерам реестра: не помещается — ошибка запуска
  (переиспользование готового пасса не блокируется), впритык — предупреждение; `process --plan` печатает советы.
  Экспорт VDA без нулевых констант внимания (≈ 1 ГБ меньше ONNX и движка при окне 32), граф больше 1.9 ГБ — с
  внешними данными `.onnx.data`; веса Base и Large — закреплённая HF-ревизия и sha256. Смена бэкенда убирает модель
  чужого списка. Пассы VDA-Small, DA3 и stub не пересчитываются. Замер на RTX 4070 Ti SUPER 16 ГБ: Large с обученным
  окном 32 — 10.1 ГБ на 1080p, +45–65 % времени к Small; Base — 5.3 ГБ, +33–42 %. Для этого рабочая память сборщика
  TensorRT поднята с 2 ГиБ до половины свободной видеопамяти, экспорт идёт без autograd (Large при окне 32 падал по памяти),
  внимание DINOv2 — через SDPA. По TAE на 5 клипах крупные модели не лучше Small однозначно (`docs/benchmarks.md`).
Дефекты сверки ТЗ с реализацией (TASK-0038, `Output/spec-audit` рабочего пространства) и находки ревью этих исправлений.

- Векторы движения y-up (аудит pass-mv-yup). Флаг `mv.y_up` манифеста раньше только записывался: `PassReader` теперь
  отдаёт кадры такого пасса уже y-down (знак v меняется при чтении), `PassWriter` всегда пишет y-down, CLI `import` /
  `convert` / `export` принимают `--y-up`; папка с манифестом читается по нему и с `--pass` (раньше пересканировалась и
  теряла флаг), `convert` отказывает в паре, которая не конверсия. У пасса без отпечатка ориентация входит в его
  псевдо-отпечаток: переключение флага пересчитывает upscale, nr и fg.
- Падение FG больше не обрывает «Обработать» (аудит fg-2). В `process` стадия FG работает в дочернем `dlssvid fg
  --as-stage` (job object, протокол `@progress` / `@result`): при падении или зависании стадия помечается failed с кодом
  выхода, недописанный `color_fg` удаляется (в том числе перезаписанный на месте), результат кодируется из `color_nr`,
  задача GUI завершается успешно с предупреждением. Отладка без изоляции — скрытый `--fg-in-process`.
- Воспроизведение с точной частотой (аудит play-fg-rate). FG-результат 48 fps играл на 50 Гц (таймер 20 мс): теперь
  кадры показывают часы с рациональной частотой самого быстрого видимого источника, по одному кадру за тик, без дрейфа
  (24000/1001 тоже), с ожиданием медленного декода до 2 с; кадр рисуется синхронно с тиком.
- Временное выравнивание глубины включено по умолчанию (аудит depth-7). Окно центрированное, ±N кадров
  (`stabilize_window` теперь радиус, по умолчанию 8; выход задержан на N кадров); `auto` для metric-моделей — только
  масштаб, для относительных — масштаб и сдвиг; рекурсии по выровненным кадрам нет. Сегмент рвётся на склейке, на скачке
  разброса и вокруг кадра без глубины, масштаб кадра ограничен 1/1.5…1.5, дыры заполняются после выравнивания. Замер на
  пяти клипах: TAE DA3 ниже в 1.1–2.9 раза, VDA — до 1.3 раза (`docs/benchmarks.md`). Ревизия стадии `depth.2` в
  `tool.app`: пассы глубины прежних версий (и `dlssvid depth` без отпечатка) пересчитываются один раз; при
  `stabilize=none` — нет.
- Флаг ×1 (аудит sr-5): «Без масштабирования (×1)» и CLI `--no-scaling` (старое имя `--artifact-reduction-only`
  принимается) — подпись соответствует тому, что флаг делает.
- «Запустить этап» в GUI отказывал на любом изменённом параметре глубины (`--input_size`), потоков, апскейла и NR
  (`jitter`, `target_width`, `guides` …): аргументы строит `StageCliArgs` по схеме параметров, команды принимают ключи
  схемы; тест сверяет каждый параметр каждой стадии с `--help` её команды.
- История версий пассов: две версии, созданные в одну секунду, упорядочиваются по времени записи манифеста, а не по
  отпечатку — очистка истории могла удалить более новую, и возврат параметра пересчитывал вместо восстановления.
- `GpuFrameCache` переиспользует текстуры пассов слота для следующего кадра вместо новой аллокации на каждый кадр.
- Бенч `tests/data/bench_clips.py`: папка глубины очищается перед прогоном, пасс векторов проверяется на длину клипа
  (тест `scripts.bench_clips`).
- CI: шаг `release.yml`, прикладывающий пакет к Release тега, падал, когда Release ещё нет (тег v0.4.0): Windows
  PowerShell 5.1 обрывал шаг на «release not found» из stderr `gh`. Логика вынесена в `scripts/attach_release.cmd` (cmd,
  пакет по версии из тега, а не первый ZIP в папке); регрессионный тест `scripts.attach_release` гоняет скрипт против
  поддельного `gh`. Release 0.4.0 создан вручную из артефакта прогона тега.

## 0.4.0 — 2026-10-12

Весь пайплайн без потери разрядности: 10-битный (и 12/16-битный) источник проходит декод, конверсию и кодирование в
своей разрядности и цветности, результат пишется в HEVC Main 10 / 4:4:4, AV1 10 бит, FFV1 или новый ProRes, формат виден в
CLI, отчёте и GUI; замер подтвердил, что DLSS SR, NR и DLSS-G сохраняют 10-битные градации; CI устойчив к срывам реестра
vcpkg, тег собирает только пакет.

- 10-битный пайплайн (TASK-0034). Декодер отдаёт кадр в раскладке источника — 8, 10, 12 или 16 бит, 4:2:0 / 4:2:2 / 4:4:4
  (HEVC Main 10 и Rext, AV1 10 бит, ProRes, FFV1; NVDEC и ПО-декод совпадают бит-в-бит), раньше всё, что не 8 бит 4:2:0,
  приводилось к нему через swscale. Конверсия в RGBA16F идёт из N бит, кодировщик пишет 10 бит: HEVC NVENC Main 10 и
  4:4:4 (Rext), AV1 NVENC 10 бит, FFV1 8/10/12/16, новый ProRes (`prores_ks`: 422 HQ / 4444, `.mov`); в поток пишутся
  цветовые теги (матрица и диапазон, primaries и transfer источника), HEVC в MP4/MOV получает `hvc1`. Разрядность и
  цветность результата — «Авто» (разрядность источника в пределах кодека; 4:2:0 для NVENC, 4:2:2 для ProRes, как у
  источника для FFV1) или явно: CLI `--bit-depth auto|8|10|12`, `--chroma auto|420|422|444`, карточка «Кодирование» в GUI
  (хранится в проекте); H.264 NVENC остаётся 8-битным. Формат виден в `dlssvid info` (`samples:`), отчёте `process` и его
  JSON (`output_format`), в GUI — в «Источник», «Что получится» и строке результата; расширение результата следует
  кодеку (.mp4 / .mov / .mkv). Отпечатки пассов учитывают раскладку декодированного источника (пассы 8-битных источников
  не пересчитываются, пассы 10-битных — один раз).
- Разрядность внутри DLSS измерена (TASK-0035): руководство DLSS обещает квантовку до 8 бит в LDR-режиме, но пологая
  10-битная рампа проходит DLSS SR, NR и DLSS-G с шагом в один 10-битный код (`docs/benchmarks.md` «Разрядность по
  пассам») — HDR-режим DLSS не нужен и не включён; тест `[precision]` (`tests/integration/test_precision.cpp`) сторожит
  это на GPU-прогонах и проверяет сам метод на NIS без GPU.
- CI: `scripts/configure.cmd` — configure с повтором до 3 раз (загрузка реестра vcpkg с GitHub на раннере срывается время от
  времени); теги обрабатывает отдельный `release.yml` — только сборка пакета и его прикрепление к Release, без повторного
  build-test (merge-коммит уже проверен в pull request и на `main`).

  (`yuv444p16le`), 10/12-бит (`p010`, `p016`): «NVDEC frame is not NV12». Теперь декодер отдаёт для таких потоков кадр на

  прикладывается к Release; процедура выпуска в `docs/release.md`.
- `scripts/setup_sdk.py`: сторонние SDK и чекауты кода моделей на закреплённых ревизиях (DLSS SDK 310.9.1, Optical Flow SDK,

  Загрузчики `vda_loader.py` / `searaft_loader.py` ищут чекауты там же вместо пути машины разработки.

  картинки README существуют, не тяжелее 4 МБ (30 МБ вместе) и перечислены в `docs/media/README.md`.

## 0.3.0 — 2026-09-25

Открытые нейросетевые апскейлеры рядом с DLSS SR, стартовый экран и карточки стадий по макетам, воспроизведение без
мерцания, битрейт по умолчанию; README для публикации на GitHub (сборка, установка, модели, рантаймы NVIDIA), `sr_worker/`
в пакете.

- Кодирование: битрейт по умолчанию подбирается по разрешению, частоте и кодеку результата (`core/io/EncodeDefaults`:
  H.264 1080p30 ≈ 16, 4K30 ≈ 45, 4K60 ≈ 70 Мбит/с; HEVC ≈ 0,65×, AV1 ≈ 0,55×) и в CLI, и в GUI — раньше без `b` NVENC
  кодировал 3840×1600 при ~1,4 Мбит/с. Карточка «Кодирование»: «Авто» с показом выбранного значения, пресеты 20 / 35 /
  50 / 80 / 120 / 200 Мбит/с, «Свой…» в Мбит/с, оценка размера файла; для FFV1 битрейта нет («без потерь»).
  В CLI явное значение — `--codec-opt b=50M`, лог сообщает выбранный автоматически.
- Оформление GUI по макетам (`app/Theme`): тёмная палитра и таблица стилей с размерами и отступами из макетов —
  кнопки 36 px (главное действие в акценте 48 px), табличные 24 px, сегменты 32 px, чипы 30 px, поля 30 px,
  карточки 9×14 px, панели 48 px; переключатель «Инженерный режим» — флажок. Колесо мыши над невыделенным списком,
  счётчиком или слайдером прокручивает страницу, а не меняет значение (раньше прокрутка панели проекта могла
  переключить бэкенд стадии).
- Таймлайн: кнопки воспроизведения нарисованы в цвете текста темы (стандартные иконки Fusion терялись на тёмной
  панели); кнопка-переключатель зацикливания (`L`, пункт в меню «Вид», запоминается в QSettings) — по концу
  ролика воспроизведение начинается сначала.
- Вьюпорт: пока точный кадр источника ещё грузится, на экране остаётся ближайший загруженный кадр этого источника

  отстающем тике ячейка уходила в серую плашку или в чёрный). Подпись ячейки и пробник честно пишут «загрузка…»,
  пока показан предыдущий кадр; кадра нет — по-прежнему штриховка. Воспроизведение показывает каждый кадр: тик ждёт,
  пока у всех показанных источников загрузится следующий кадр (медленный декод играет медленнее реального времени,
  а не пропускает кадры); кадр, не пришедший за 2 с, пропускается.

### Пайплайн и CLI
- Отпечаток пасса (sha256 канонического JSON: хэш исходника, стадия, параметры с умолчаниями схемы, отпечатки входов,
  инструмент — бэкенд, модель, DLL NVIDIA) в `manifest.json`; пасс переиспользуется только при совпадении отпечатка,
  смена параметра пересчитывает стадии ниже по цепочке. Пассы без отпечатка (0.1.0) усыновляются как `legacy`.
- Версии пассов: текущая — `<passes>/<pass>/`, предыдущие — `<passes>/<pass>.v/<YYYYMMDD-HHMMSS_fp8>/`; хранятся две
  последние (`pass_versions_keep` в проекте), сборщик не удаляет версии, на которые ссылаются входы других версий.
- `dlssvid process --plan` (решения reuse / run / restore с причинами), `--keep-versions`, `--force stage,…`; `dlssvid
  passes list|use|gc`; параметры стадий проверяются по схеме (`core/stages/ParamSchema`) в CLI и GUI; кодер и опции
  кодирования — из файла проекта; оценки времени и диска прогона (`core/pipeline/Estimates`); `dlssvid render --time`.
- Файл проекта: `viewport.time` в секундах вместо `frame` (старые проекты читаются как `time = frame / fps`), поля
  `pass_versions_keep`, `encode`, `source_hash` (кэш хэша исходника по размеру и mtime).

### Исправления
- `FrameStore`: зависание при остановке (потерянное пробуждение загрузчика) — стресс-тест.
- Векторы движения внутри `process` снова декодируют видео через NVDEC после стадии глубины: FFmpeg отказывал в NVDEC
  из-за флагов первичного CUDA-контекста; декодер выравнивает их (`cudaSetDeviceFlags`).
- Открытие видео только ради информации о потоке логируется на уровне debug (одна строка «open» на чтение).
- Тесты: QSettings тестов — INI-файл на процесс; тесты запускаются из папки вне клона (обновлятор NGX
  `nvngx_update.exe` наследовал рабочую папку и ронял `git clean` в CI).
- Кэш TensorRT-движков пишется и читается по путям длиннее 260 символов (`Win32LongPath`, префикс `\\?\`): пакет,
  распакованный в глубокую папку, собирал движок несколько минут и не мог его сохранить.

Тесты: 217 (юнит, интеграционные, приложение, golden). Golden-эталоны не менялись.
